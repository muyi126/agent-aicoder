# Bug Fix Skill

当用户要求修复 bug、调查错误或解释为什么某事失败时使用。

目标不是快速猜测原因。

目标是复现、隔离、修复和验证。

---

## 工作流程

### 1. 理解 Bug

在改变代码前，识别：

- 观察到的行为是什么？
- 预期行为是什么？
- 何时开始发生？
- 有错误消息、日志、堆栈跟踪、截图或失败测试吗？
- 哪些用户、环境、平台或版本受影响？

若 bug 报告模糊，请求缺失的复现细节。

### 2. 先复现

不要修复尚未复现或未清楚推理的 bug。

首选以下复现形式之一：

- 失败的单元测试
- 失败的集成测试
- 简单手动复现
- 指向失败路径的日志或堆栈跟踪

若当前环境无法复现，明确说明。

### 3. 隔离根本原因

编辑前，解释可能的原因。

对于涉及多个文件的非平凡 bug，使用 **Explore 子代理**定位可疑调用点，而非污染主会话。

好的根本原因声明示例：
```text
崩溃发生是因为 `user.profile` 可能为 null，但 `renderAvatar` 在没有 null 检查的情况下读取 `user.profile.avatarUrl`。
```

坏的根本原因声明示例：
```text
这可能是状态问题。
```

要具体。

### 4. 做最小修复

用最小安全变更修复 bug。

不要：
- 重写整个模块
- 重命名无关变量
- 重格式化无关文件
- 添加新抽象除非必要
- 修复附近问题除非它们是同一 bug 的一部分

每个变更的行必须与 bug 相关。

### 5. 验证修复

运行最相关的检查：

- 失败测试
- 相关单元测试
- 类型检查
- Lint
- 构建
- 手动复现步骤

若检查无法运行，解释原因。

---

## Guardrails

若 bug 修复触及以下内容，停止并请求人工确认：

- Auth 或权限逻辑
- 支付逻辑
- 数据迁移
- 安全敏感代码
- 公共 API 行为
- 大规模重构

---

## 与其他 Skill 的连接

### 来自 execute-tasks
当在任务执行中发现 bug 时：
1. 修复 bug
2. 不中断工作流地继续剩余任务
3. 记录修复以供后续审查

### 来自 review-code
当在代码审查中发现 bug 时：
1. 修复 bug
2. 将修复详情添加到审查报告
3. 继续审查

### 独立使用
可通过说"修复这个 bug"或"处理这个问题"触发。
完成时输出修复报告。
