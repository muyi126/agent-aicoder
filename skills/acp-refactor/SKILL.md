# Refactor Skill

当用户要求重构、清理、简化、模块化或架构改进时使用。

重构的目标是在保持行为的同时改进结构。

若行为变更，则不仅仅是重构。

---

## 重构规则

### 1. 定义重构目标

编辑前，陈述精确目标：

- 减少重复
- 改进命名
- 提取函数
- 拆分大模块
- 移除死代码
- 改进可测试性
- 简化控制流

不要仅仅因为代码看起来旧或丑就重构。

### 2. 保持行为

除非用户明确要求，否则公共行为必须保持不变。

编辑前，识别：
- 公共 API
- 输入/输出行为
- 现有测试
- 兼容性要求
- 已知边缘情况

### 3. 小步骤重构

偏好小、可逆的变更。对于多步骤重构，创建 TodoWrite 列表，使每步（重命名、提取、移动、去重）被追踪且可独立验证。

好的步骤：
- 重命名一个概念
- 提取一个函数
- 移动一个辅助函数
- 移除一个重复
- 在重构前添加一个缺失的测试

坏的步骤：
- 重写整个模块
- 一起改变命名、结构和行为
- 引入框架
- 无清晰边界地拆分文件

### 4. 频繁运行检查

每有意义步骤后，尽可能运行相关检查：

- 现有测试
- 类型检查
- Lint
- 构建

若检查不可用，解释风险。

---

## 输出格式

```text
重构目标:
- ...

行为保持:
- ...

变更:
- ...

验证:
- ...

风险:
- ...
```

---

## 停止条件

若以下情况，停止并请求确认：

- 重构需要公共 API 变更
- 变更触及高风险模块
- diff 超出预期
- 发现代码需要重新设计而非重构。在这种情况下，退出重构模式并在继续前通过计划模式（ExitPlanMode）提出计划。
