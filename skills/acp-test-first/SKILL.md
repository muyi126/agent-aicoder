# Test First Skill

当用户要求修复 bug、添加行为或做可透过测试验证的变更时使用。

目标是让测试在实现细节变更之前描述预期行为。

---

## 何时使用

使用此 skill：
- Bug 修复
- 行为变更
- 边缘情况处理
- 回归预防
- 需要安全覆盖的重构

若项目没有测试框架或任务纯粹是探索性的，不要强制 test-first 工作。在这种情况下，文档化缺失的测试环境。

---

## 工作流程

### 1. 定义预期行为

在写代码前，写下：

- 应该发生什么？
- 当前发生什么？
- 什么输入触发行为？
- 应观察到什么输出、状态或副作用？

### 2. 写或识别失败测试

首选因正确原因失败的测试。

好的失败测试是：
- 专注的
- 易理解的
- 与用户请求相关
- 不耦合到不必要的实现细节

避免仅验证mock内部函数被调用的测试，除非那才是实际契约。

### 3. 做最小实现变更

仅改变使测试通过所需的代码。

不要：
- 重写附近代码
- 添加通用抽象
- 改变公共 API除非需要
- 在同一步骤中添加无关测试用例

### 4. 再次运行测试

实现后：
- 运行新的或改变的测试
- 运行相关测试
- 运行类型检查、lint 或构建（如果有）

若检查无法运行，清楚说明。

---

## 输出格式

```text
预期行为:
- ...

失败测试:
- ...

实现:
- ...

验证:
- ...

未验证:
- ...
```

---

## Guardrail

不要仅仅为了匹配错误实现而改变测试。

若测试揭示需求模糊或错误，停止并请求澄清。
