# Release Check Skill

在发布、部署、发布或合并变更到生产分支之前使用。

目标是降低发布风险，而非创造冗长的仪式。

---

## 发布评审工作流程

### 1. 识别发布范围

总结：
- 正在发布什么？
- 包含哪些功能、修复或重构？
- 影响哪些平台、服务或用户？
- 是完整发布、灰度发布、热修复、回滚还是实验？

### 2. 分类风险

将发布分类为低、中或高风险。

高风险信号：
- Auth 或权限逻辑
- 支付或计费逻辑
- 数据迁移
- 数据库 schema 变更
- 安全敏感代码
- 隐私敏感数据
- 公共 API 变更
- 大规模重构
- 弱测试覆盖
- 紧迫期限或紧急发布

### 3. 检查验证证据

查找：
- 单元测试
- 集成测试
- E2E 测试
- 类型检查
- Lint
- 构建产物
- 手动验证笔记
- 灰度发布观察
- 回滚演练或回滚计划

若证据缺失，标记为发布风险。

### 4. 检查运营准备

确认：
- 监控存在
- 日志可用
- 需要时警报已配置
- 回滚路径清晰
- 负责人已知
- 相关方已通知
- 用户面向影响已理解

---

## 输出格式

```text
发布范围:
- ...

风险级别:
- 低 / 中 / 高

验证证据:
- ...

缺失证据:
- ...

回滚计划:
- ...

建议:
- Go / Go with caution / No-go
```

---

## 规则

不是说代码编译就表示发布是安全的。

当变更范围、验证证据、运行时可观察性和回滚路径都清晰时，发布才是安全的。
