# Plan Task Skill

当工作太大或太模糊以至于无法直接开始编码时使用。

目标不是为计划而写计划。

目标是产生最小计划使执行安全——明确范围、明确非目标、明确验证、明确交接。

---

## 何时使用

以下任一情况为真时使用此 skill：

- 变更跨越超过 2-3 个文件且接触点不明显
- 请求混合多个关注点（重构 + 功能 + bug 修复）
- 成功标准尚未定义
- 用户说"设计"、"架构"或"找出如何"而非"做"
- 将进入高风险区域（auth、支付、迁移、公共 API）

若任务小而明显，跳过此 skill 直接进入 `acp-bug-fix`、`acp-refactor` 或 `acp-feature-add`。

---

## 工作流程

### 1. 重申目标

用一到两句话写下成功是什么样子的（从用户角度）。

若无法做到，则任务尚未准备好进行计划——回去问用户。

### 2. 映射表面区域

使用 **Explore 子代理**识别（不污染主会话）：

- 可能涉及的文件和模块
- 工作应遵循的现有模式
- 已覆盖受影响行为的测试
- 风险（高风险模块、公共 API、数据路径）

在计划中引用文件路径，以便审查者验证你的读取是正确的。

### 3. 分解为可验证步骤

将工作分解为每步都满足的步骤：

- 做单一概念性变更
- 结束于可运行验证的状态（测试通过、构建成功）
- 可独立回退

坏：重写 auth 模块
好：1. 添加 X 的失败测试；2. 提取辅助函数 Y；3. 交换实现；4. 删除旧路径

将步骤记录在 TodoWrite 列表中，使执行期间进度可见。

### 4. 前置定义验证

每步写下如何验证：

- 更新或添加了哪个测试文件
- 运行什么命令（`pnpm test`、`cargo check`、...）
- 什么手动重现会证明它

没有验证路径的步骤不是步骤——是愿望。

### 5. 使用计划模式获取签署

通过 **ExitPlanMode** 展示计划，以便用户可以在写任何代码前批准或推回。

在计划被批准前不开始编辑。

### 6. 交接给执行 Skill

批准后：
- Bug 修复 → `acp-bug-fix` skill
- 保持行为的清理 → `acp-refactor` skill
- 新行为 → `acp-feature-add` skill
- Test-first 变更 → `acp-test-first` skill

此 skill 结束于交接。

## 输出格式

```text
目标:
- ...

非目标:
- ...

受影响文件/模块:
- ...

风险:
- ...

步骤:
1. <步骤> — 验证方式 <如何>
2. <步骤> — 验证方式 <如何>
3. ...

交接:
- 这将在 <skill-name> skill 下执行
```

---

## Guardrails

若以下情况，停止并请求用户继续：

- 计划增长超出用户描述的范围
- 步骤触及高风险区域（auth、支付、迁移、安全、隐私、公共 API）
- 意识到请求实际上是两个独立任务。在这种情况下，建议拆分它们。
