# Feature Add Skill

当用户要构建新东西时使用——功能、端点、页面、组件或能力。

目标不是尽可能快地开始打字。

目标是澄清契约、计划最小可行实现，并在声称完成前验证新行为确实有效。

---

## 工作流程

### 1. 澄清契约

在写代码前，写下：

- 新行为是什么？
- 输入是什么？
- 输出、副作用或状态变更是什么？
- 谁调用这个？谁受影响？
- 什么明确在范围外（非目标）？
- 什么现有行为必须保持不变？

若任何一项不清，问。不要发明需求。

### 2. 计划先行

对于超出简单 1 文件变更的任何内容，在编辑前进入**计划模式**（ExitPlanMode）。

好的计划回答：

- 将创建或修改哪些文件？
- 满足契约的最小变更集是什么？
- 代码库中有现有模式可遵循吗？使用 Explore 子代理查找，而非发明新模式。
- 验证策略是什么？

在写代码前获得计划批准。

对于多步骤功能，也创建 TodoWrite 列表，使进度可见且每步结束于可验证状态。

### 3. 先复用再创建

在添加新抽象前：

- 在代码库中搜索已存在的工具、组件或模式
- 偏好扩展现有事物而非创建新的通用事物
- 除非替代方案明显更差，否则不引入新依赖

仅有一个调用者的新通用辅助函数是异味，不是功能。

### 4. 实现最小可行版本

构建满足契约的最小版本。

不要：
- 添加无人要求的配置选项
- 添加「以后可能有用」的字段
- 为假设的第二个调用者添加抽象
- 包装现有库除非有具体原因

若发现自己想要泛化，停止并先完成具体案例。

### 5. 端到端验证

新功能在文件编译时不表示完成。

按偏好顺序运行：

- 锻炼新行为的测试（若项目支持测试则写一个）
- 相关类型检查、lint 和构建命令
- 手动重现用户面向路径

若验证无法在当前环境运行，明确说明。

## Guardrails

若以下情况，停止并请求确认：

- 功能触及 auth、权限、支付、数据迁移、安全、隐私、公共 API 或发布流程
- 功能需要更改公共 API 或破坏向后兼容性
- 计划增长超出用户声明的范围
- 实现需要新框架或主要依赖
